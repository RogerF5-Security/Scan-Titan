Vulnerability Scanner · Python · Windows y Linux

Scan TitanCómo funciona

Scan Titan es un escáner de vulnerabilidades que reconoce la superficie de un objetivo autorizado, ejecuta pruebas propias y de herramientas externas, valida cada hallazgo con controles comparativos y conserva un histórico para saber si la exposición sube o baja con el tiempo.

Esta página explica qué hace en cada etapa, cómo decide qué es una vulnerabilidad y qué no, y qué archivos entrega al terminar.

01 / Qué hace

Cinco tareas,
un solo flujo.

Una ejecución procesa cada objetivo de targets/targets.txt sin preguntas interactivas. Lo que encuentra pasa por las mismas reglas de calidad antes de llegar a los reportes.

RECONOCE

Superficie real

Puertos, servicios, tecnologías, WAF/CDN, subdominios, rutas, APIs y JavaScript del objetivo.

PRUEBA

Pruebas activas

Inyecciones, CORS, redirecciones, autenticación, autorización, TLS, cabeceras, archivos expuestos y servicios.

VALIDA

Prueba reproducible

Compara cada señal contra un control. Lo que no se puede demostrar queda en «Por validar».

REPORTA

Evidencia y comando

Cada hallazgo lleva evidencia técnica, riesgo, CWE/OWASP y un comando para repetir la prueba.

SIGUE

Histórico

Identidad estable por vulnerabilidad: sabe cuándo apareció, si persiste, si se corrigió o si volvió.

02 / Cómo funciona

El pipeline,
etapa por etapa.

Por defecto se procesan dos objetivos a la vez bajo un límite global de 20 peticiones HTTP. Cada módulo tiene presupuesto de pruebas y timeout propios: si uno se agota, se registra y el pipeline continúa.

  1. 01PREPARACIÓN

    Alcance y comprobación previa

    Lee los objetivos, valida la configuración YAML, comprueba dependencias y herramientas instaladas y verifica si el objetivo responde por HTTP. Un equipo sin web continúa con las pruebas de infraestructura.

    • python main.py --health-check
    • Configuración inválida detiene la ejecución en lugar de usar valores por defecto.
    • Objetivos sin respuesta quedan marcados en la cobertura.
  2. 02RECONOCIMIENTO

    Inventario del objetivo

    Nmap enumera puertos y versiones; WhatWeb identifica tecnologías; wafw00f detecta WAF/CDN; subfinder, Katana y httpx amplían hosts y rutas. El análisis de JavaScript extrae endpoints, APIs y librerías.

    • Correlación de versiones con un catálogo local de avisos y fin de soporte.
    • Una sola recolección se reutiliza entre módulos.
  3. 03SUPERFICIE

    Rutas que existen de verdad

    El descubrimiento prueba primero las rutas de mayor valor (repositorios, backups, configuración, paneles, logs) y luego el diccionario. Un oráculo soft-404 pide rutas aleatorias por origen, directorio y extensión para descartar páginas que responden 200 a todo.

    • ffuf recibe solo entradas aún no probadas.
    • 401/403 se registran como reconocimiento, no como vulnerabilidad.
  4. 04PRUEBAS

    Módulos propios y motores externos

    28 módulos asíncronos prueban la aplicación y sus servicios. Nuclei aporta firmas de CVE y exposiciones; OWASP ZAP añade spider, AJAX spider y análisis activo; Nmap NSE revisa TLS, SSH, SMB y UDP.

    • Ajuste adaptativo ante bloqueos de WAF y respuestas estables.
    • Perfiles zero-touch, --full y políticas seguras.
  5. 05VALIDACIÓN

    Control contra prueba

    Las inyecciones se repiten de forma independiente: una petición de control sin payload y otra con payload, al menos dos veces. Solo se confirma si la diferencia es reproducible. Las alertas sin prueba se clasifican como «Por validar».

    • XSS escala a payloads según el contexto HTML donde se refleja.
    • Command injection exige dos resultados aritméticos distintos.
  6. 06ESTADO Y REPORTES

    Identidad, histórico y entregables

    Cada hallazgo recibe un identificador canónico estable (mismo tipo, mismo servicio, mismo parámetro), aunque la herramienta lo titule en otro idioma o cambie la URL exacta. Con ese estado se generan el Daily, el informe formal y la matriz Excel.

    • Estados: nuevo, recurrente, regresión, ya no visto.
    • Las decisiones de descarte del analista se aplican en escaneos futuros.

03 / Precisión

Cómo evita
falsos positivos.

Un escáner que avisa de todo obliga a revisar todo. Scan Titan separa lo demostrado de lo que solo es una señal, y dice por qué.

Oráculo soft-404

Muchos sitios responden 200 a rutas inexistentes. Antes de aceptar una ruta, se compara su respuesta con la de rutas aleatorias del mismo directorio y extensión.

Similitud ≥ 90% con el control → descartada

Contenido probatorio

Una ruta expuesta solo cuenta si su contenido lo demuestra: estructura de .git/config, líneas de log con fecha y nivel, firma de listado de directorio.

HTTP 200 sin contenido esperado → no es hallazgo

Validación diferencial

SQLi, XSS y traversal se repiten con control y prueba independientes. La evidencia guarda la diferencia observada y el número de repeticiones.

Diferencia reproducida 2/2 → confirmada

Por validar

Correlaciones por versión (Nmap vulners), heurísticas NSE y alertas activas sin evidencia de respuesta no se cuentan como vulnerabilidades.

Señal sin prueba → «Por validar», fuera de las métricas

Identidad estable

El mismo fallo reportado en español e inglés, o en URLs distintas del mismo servicio, se fusiona en un solo registro. Las cookies se identifican por servicio y nombre.

Sin rotación falsa de nuevas/resueltas

Laboratorio de verificación

tools/vuln_lab.py levanta en loopback un servidor con vulnerabilidades conocidas, controles negativos y señuelos, ejecuta el pipeline y comprueba cada comando de verificación.

Mide detección esperada, falsos positivos y comandos
VALIDADO

Prueba diferencial o contenido probatorio. Cuenta como vulnerabilidad.

OBSERVADO

Configuración verificable directamente en la respuesta (cabeceras, cookies, TLS).

POR VALIDAR

Correlación o heurística sin prueba. Visible para el analista, fuera de los conteos.

Comandos que muestran la prueba

Cada hallazgo incluye un comando PowerShell que repite el control y la prueba e imprime la línea de estado, el texto que demuestra el fallo y el tiempo de respuesta. Las rutas incluyen una petición a una ruta inexistente para comparar.

# Scan Titan: reproducir validacion diferencial confirmada.
Write-Host '[baseline]'; $l = @(curl.exe -k -sS -i --max-time 30 -w 'ST_TIME=%{time_total}s' -- 'https://shop.example.com/search')
$l[0]; $l | Select-String -SimpleMatch '<svg onload=st7f3>' | Select-Object -First 5
Write-Host '[probe]'; $l = @(curl.exe -k -sS -i --max-time 30 -w 'ST_TIME=%{time_total}s' -- 'https://shop.example.com/search?q=%3Csvg%20onload%3Dst7f3%3E')
$l[0]; $l | Select-String -SimpleMatch '<svg onload=st7f3>' | Select-Object -First 5

04 / Daily Report

Vulnerabilidades
a lo largo del tiempo.

Daily_vulns_report.html es un único archivo HTML, sin conexiones externas, que reúne lo detectado por Scan Titan y permite ver si la exposición sube, baja o se mantiene. Las capturas usan datos ficticios.

¿Sube o baja?

Barras apiladas por severidad para cada fecha con escaneo, en periodos de 7, 30 o 90 días o todo el histórico, filtrables por objetivo.

  • Nuevas frente a resueltas por fecha, con el cambio neto.
  • Tabla diaria: al pulsar una fecha muestra qué apareció y qué se resolvió.
  • Tendencia por objetivo, mapa de calor objetivo × fecha, antigüedad y reincidencia.

Antes y después

Elige dos fechas cualesquiera, por ejemplo antes y después de aplicar parches.

  • Vigentes en cada fecha y variación por severidad y por objetivo.
  • Listas de vulnerabilidades nuevas, resueltas y persistentes.

Un lugar para todo lo detectado

Catálogo agrupado por tipo de vulnerabilidad, con buscador y filtro por severidad.

  • Objetivos afectados, casos y cuántos tienen prueba.
  • Tendencia de las últimas 30 fechas y fecha de primera detección.
  • Cada fila se despliega en sus casos concretos.

Registro operativo

Vistas de vigentes, por validar, nuevos, regresiones, no vistos y descartados.

  • Filtros por severidad, objetivo, categoría, motor y confianza.
  • Riesgo combinado: CVSS, confianza, evidencia, exposición, recurrencia y criticidad del activo.
  • Descartes del analista exportables; con Abrir_Daily.cmd el motor los aplica en el siguiente escaneo.

Evidencia y prueba manual

El detalle reúne severidad, estado, evidencia, CWE, URL, parámetro, motores, primera y última detección.

  • Comando de verificación listo para copiar.
  • Evidencia técnica de la respuesta que confirmó el hallazgo.
Arrastre del último estado

En cada fecha, cada objetivo aporta su último escaneo hasta ese día. Un objetivo no escaneado no cuenta como «resuelto».

Sin respuesta ≠ corregido

Si un objetivo no responde por HTTP, se conserva su último estado observado y la fecha lo indica.

Mismas reglas en el pasado

Las reglas de calidad se aplican también a reportes antiguos, para que la serie no baje solo por un cambio de criterio.

05 / Motores

Módulos propios
y herramientas externas.

Las herramientas externas se ejecutan de una en una y sus resultados pasan por las mismas reglas que los módulos propios. Si una no está instalada, se registra y el resto continúa.

NMAPRED

Puertos y servicios

Versiones con -sV y perfiles NSE separados: vulnerabilidades seguras, TLS, Slowloris, Vulners/CVSS, SSH, SMB y UDP.

NUCLEIFIRMAS

CVE y exposiciones

Cinco perfiles: vulnerabilidades, conservador, CVE, servicios de red y DAST sobre URLs con parámetros.

OWASP ZAPDAST

Spider y escaneo activo

Daemon local por API, spider clásico y AJAX, importación de OpenAPI/GraphQL y modos pasivo, baseline o activo.

FFUFRUTAS

Fuzzing de rutas

Recibe las entradas que el descubrimiento interno aún no probó, con filtro de respuestas soft-404.

WHATWEB · WAFW00FHUELLA

Tecnologías y perímetro

Servidores, frameworks, CMS y plugins; proveedor de WAF/CDN con evidencia y confianza.

SUBFINDER · KATANA · HTTPXRECON

Hosts y rastreo

Subdominios pasivos del dominio registrable, rastreo acotado de la aplicación y sondeo HTTP de hosts.

Módulos propios

Escritos en Python asíncrono, con presupuesto de pruebas y timeout por módulo. Playwright se usa para la auditoría en navegador y el XSS almacenado.

Monitor
en tiempo real.

Progreso global y por módulo, hallazgos, actividad HTTP y consumo de CPU/RAM de Scan Titan y sus procesos hijos. Desde la consola, en Windows: P pausa, R reanuda y F finaliza generando los reportes con lo encontrado.

07 / Instalación y uso

Preparar una vez.
Ejecutar con una orden.

Requiere Python 3.11 o posterior. El instalador prepara las dependencias de Python y, si se autoriza, las herramientas externas; el health-check informa de lo que falte.

WINDOWS / POWERSHELL
git clone https://github.com/RogerF5-Security/Scan-Titan.git
cd Scan-Titan
python -m venv .venv
.\.venv\Scripts\Activate.ps1
powershell -ExecutionPolicy Bypass -File .\install\install.ps1
python main.py --health-check
python main.py
LINUX / BASH
git clone https://github.com/RogerF5-Security/Scan-Titan.git
cd Scan-Titan
python3 -m venv .venv
source .venv/bin/activate
bash install/install.sh
python main.py --health-check
python main.py

08 / Límites

Qué no promete.

Un resultado automatizado es un punto de partida para el analista, no una conclusión de auditoría.

Cobertura

Ninguna prueba automatizada garantiza encontrar todas las vulnerabilidades. Lógica de negocio, autorización entre usuarios y flujos con estado requieren configurar identidades y casos, y revisión manual.

WAF empresariales

Las variaciones de codificación y cabeceras pueden superar filtros básicos. Ante WAF con reputación, rate limiting y reglas administradas no hay bypass automático: el analista ajusta concurrencia y payloads.

Explotabilidad

Una vulnerabilidad validada demuestra el comportamiento, no el impacto completo en el negocio. Los comandos incluidos sirven para confirmarla y documentarla.

Uso autorizado

Ejecuta el motor solo contra activos incluidos en un alcance escrito. Objetivos, reportes, sesiones y evidencias permanecen en el equipo local y fuera del repositorio.
